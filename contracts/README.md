# Contracts

The API contract shared by `backend/` and `frontend/`.

| File | What | Generated by |
|---|---|---|
| `openapi.json` | The API, as the running backend describes it. | `cd backend && ./mvnw verify` |
| `api-types.ts` | TypeScript types for every schema in it. | `cd frontend && npm run contracts:types` |

Both are committed, so a contract change shows up as a reviewable diff rather than as a surprise
in somebody's browser. Neither is edited by hand.

## The three steps, and where each one lives

1. **The backend exports the spec.** `OpenApiContractTests` runs during `verify`, fetches
   `/v3/api-docs` through MockMvc and writes `openapi.json`. A test rather than a plugin, because
   the only honest source of the contract is the running application — springdoc reads the actual
   controllers, the actual validation annotations and the customizers in `OpenApiConfig`.
2. **The frontend generates types from it.** `npm run contracts:types` runs `openapi-typescript`
   over `openapi.json`. **Types only, never a client.** The hand-written `*Api` services carry
   judgment a generator would flatten: `withCredentials` on every call, the audit screen's sort
   defaults, the import's `FormData` handling, the mapping from `error.code` to a sentence.
3. **CI fails on a diff.** Both workflows regenerate and `git diff --exit-code -- contracts/`
   after the build. A backend change that alters the API without the contract being regenerated
   fails there, with the command to run.

`frontend/src/app/core/api/models.ts` is now a list of aliases onto `api-types.ts` — an alias is a
claim the compiler checks, where the interface it replaced was a claim nobody checked. What that
file still owns is the *prose*: why `changedFields` holds field names and never values, why `size`
is the requested page size rather than the number of rows returned. A schema cannot say any of
that, and losing it would be the real cost of generating.

## Regenerating

```bash
cd backend  && ./mvnw verify            # rewrites contracts/openapi.json
cd frontend && npm run contracts:types  # rewrites contracts/api-types.ts
```

Run both. The second reads what the first wrote, so a spec change that is not followed by a type
regeneration fails the frontend job rather than the backend one.

## Two things that are load-bearing

**Response fields are required unless the backend says otherwise.** springdoc reads `required` from
Jakarta validation, which a response record does not carry — validating an output is meaningless.
Left alone it would make every response field optional, and `fullName` on a `not null` column would
generate as `fullName?: string`. So `OpenApiConfig.requiredUnlessNullable` inverts the default for
response schemas and the genuinely nullable components carry `@Schema(nullable = true)`. Adding a
nullable response field means adding that annotation in the same change; forgetting it makes the
generated type claim a value that can be absent, which is the one failure mode this arrangement
has. Request schemas are deliberately untouched — their `required` already comes from validation,
and `Pageable` is why the customizer is scoped rather than applied everywhere.

**Nullable means absent, not `null`.** `spring.jackson.default-property-inclusion=non_null` drops a
null field instead of writing `null`, so a nullable field is described as "not required" and never
as `type: [string, "null"]`. `nullable` appears zero times in `openapi.json`, and a test keeps it
that way. Read an optional field with truthiness or `??`, never with `=== null`.

## The output has to be byte-stable

CI diffs this file, so a document whose bytes moved between two runs of the same code would fail
innocent pull requests — and a gate that cries wolf is switched off within a week. `openapi.json`
is therefore not written as springdoc hands it over: object keys are sorted (springdoc's ordering
follows classpath scan order and JVM hash order), the `required` and `tags` arrays are sorted
because they are sets, and the JSON is rendered by hand with LF endings so the bytes do not depend
on the platform line separator. `enum` and `parameters` keep their order, which is meaningful.
`OpenApiContractTests.exportIsDeterministic` asserts the rendering half of that.
